# A grid's column order is a view, kept per table per Connection in the Core's settings

Grids can move their columns (the GridColumnOrder board): drag a header, Alt+Shift+Left and Right (DBeaver's keys, rebindable as `grid.moveColumnLeft` and `grid.moveColumnRight`), and the header menu's Move left, Move right and Reset column order. The board asks for the order to be view only and remembered per table per Connection, across closing the tab and a restart; query results move too but forget it on Run again.

**View only.** Nothing is ever sent to the server: no ALTER TABLE, and the SELECT a table grid fetches is unchanged. The table keeps its real column order; only what the grid shows, copies and exports follows the moved one.

**One mapping.** A grid's order is one array of column indexes (`src/grid/columnOrder.ts`). DataGrid builds `shownCols` from it (the order without the hidden columns) and ResultsPanel builds `shown`; ResultGrid takes it as `order` and reads every shown place through it, for the header, the cells, the copy and the widths. Rows are passed as they were loaded and never projected, so a move copies no row and allocates nothing per cell; the hidden columns now work the same way and stopped copying rows too. Selection, paste, the selection summary, cell edits, the Foreign Key arrow, filters, sort, tooltips and widths all go through that one array. Widths are measured once per set of shown columns and kept by column index, so a move never measures again.

**Where it is kept.** No store kept a table grid's view state past its tab: the widths and sort of UX step 4 live in the tab. The order goes in the Core's settings table, one row per table, `column_order:<connection id>:<table key>` (the table key is its database, schema and name), holding the column names and when it was last used (moved, or shown when its table opened). A move writes only that row: a drop, a menu item or a reset at once, a held move key once its run pauses (400 ms); the window's close request and an update's restart wait for any write still to come. The Core reads only that Connection's rows, as a range of the settings key index, and does the write, the size check and any eviction in one transaction. Per Connection the orders are bounded (2,000 tables and 4 MB; one order at most 4,096 names and 64 KB); past a bound the least recently used tables go first. The store deletes a Connection's rows in the same transaction as the Connection, so no order outlives it, and a write for a Connection that no longer exists is refused. The UI reads a Connection's orders once and caches them. Names, not positions, so a changed table still reads: names still there keep their places, a new column goes in after its neighbour in the table, a dropped one leaves, and no column is ever hidden by a stale order.

**Keys.** The move keys are marked `regionOnly` in the registry: the key bus takes them only with focus in a grid that can move columns, and leaves them to a text field or the SQL editor anywhere else (Shift+Option+Left selects a word on a Mac).

**Considered.** `UiPrefs`: one struct saved whole on every change, so every move would rewrite the theme and the editor font with it, and it is not per Connection. The browser's `localStorage`: not in the portable data folder (ADR 0006) and not removed with the Connection. Moving the columns in the SELECT: changes what the server is asked, which the view-only rule forbids, and a page would have to be fetched again for a move.
