# The Table Designer plans in the Core, and Apply runs exactly the plan

The Table Designer changes one table's columns, indexes and Foreign Keys, creates a new table and drops a table. The UI keeps only a draft (`src/design/draft.ts`) keyed by the names as loaded, turns it into `DesignEdit`s and sends a `DesignRequest { target, edits }` to the Core. The Core writes the SQL (`design::plan_design`, pure: the same request gives the same text), and Apply runs exactly that text through the 5a check (ADR 0013). What the preview pane shows, what the Production confirmation lists and what runs are the same statements.

## How a design runs

- **The request carries the loaded design (D1).** An alter or drop target holds the `TableDesign` the UI loaded. The plan is never made again from a fresh read, so the pass hashes match what was shown. Apply checks the table against the loaded design before the first write and refuses on any difference with "The table changed since it was opened. Reload it and make the change again." (S14); it is never planned again silently.
- **One plan path for everything.** Alter, New table (`DesignTarget::Create`) and Drop table (`DesignTarget::Drop`) all go through `plan_design`, `confirm_design` and `apply_design` on `ConnectionService`. New table and Drop table get the same preview, warnings, Production confirmation and Read-only refusal as an alter.
- **`PassScope::Design(connection, path)`.** A Production Apply needs a pass for this scope. The exact-set rule of 5b's `PassScope::Edits` applies: a pass covers exactly the statements it was confirmed for, the SQLite rebuild's checks included (S14), so an edited design, another table, a subset of the set, a query pass or an edits pass never authorizes it, and the reverse.
- **PostgreSQL** runs the plan in one transaction on its own client; a failure rolls everything back ("Nothing was changed. Statement 2 failed: ...").
- **SQLite** runs the plan in one transaction on the browse connection (`BEGIN IMMEDIATE`), with the rebuild's pragma lines outside it (below).
- **MySQL DDL is not transactional.** Each `ALTER TABLE` commits on its own, so the planner merges every change into one `ALTER TABLE` (`Atomic`: MySQL applies one statement all or nothing). The only split is D4: when the plan drops a Foreign Key and adds one, or drops a Foreign Key and an index on its columns, the key drops run first as their own statement (`Sequential`, 2 statements). The runner stops at the first failure and says how far it got: "1 of 2 statements were applied. Statement 2 failed: ...". The designer then reloads the table, because part of the change is on the server.
- A successful Apply adds one Query History entry with all its statements. A MySQL partial failure adds one entry with the applied statements and the error (D12); a clean failure on PostgreSQL or SQLite adds nothing, as in 5b.

## The SQLite rebuild (D8, S8, S9)

SQLite's `ALTER TABLE` only renames, adds and drops columns. Renames, safe adds, safe drops and index changes run in place in one transaction. Anything else (a type change, nullability, a default, a primary key change, a Foreign Key change, a move) rebuilds the table:

1. `PRAGMA foreign_keys = OFF`, before the transaction.
2. Drop the views that use the table, and views that use those (SQLite's rename check fails on a view that names a missing table). Their `INSTEAD OF` triggers are collected first.
3. `CREATE TABLE contura_new_<name>` from the read model plus the edits, columns in the edited order; copy the kept rows across (renamed columns mapped by loaded name); carry `sqlite_sequence`; check the row count.
4. Drop the old table and rename the new one.
5. Recreate the saved indexes (autoindexes come back through `PRIMARY KEY` and `UNIQUE` in the new `CREATE TABLE`), the new indexes, the triggers, the views and their `INSTEAD OF` triggers.
6. `PRAGMA foreign_key_check` for the table and for every table that references it. Any check that returns a row rolls the whole transaction back ("Rows in orders would break a Foreign Key. Nothing was changed.").
7. Restore `PRAGMA foreign_keys` after the transaction. The restore always runs, after a commit or a rollback.

The plan is `CopyOnly` (the SQL is shown with "Contura cannot rebuild this table safely: {reason}. Copy this SQL to run it yourself.", Apply off) when a dropped or renamed column's name is a whole word in a saved trigger or view, or when the saved table text has, outside quotes, `CHECK`, a `COLLATE` other than a column's (S4 carries column collations), `GENERATED`, `ON CONFLICT`, `WITHOUT ROWID` or `STRICT`, because the read model cannot carry them.

## Rulings from the plan (D1 to D29)

- **D1, the request carries the loaded design.** Cost: a table changed on the server since loading is refused at Apply and needs a Reload (S14).
- **D2, MySQL defaults and attributes.** `COLUMN_DEFAULT` is not SQL text, so the read model writes `default_sql` with the snapshot's rule, and reads charset, collation and `ON UPDATE` so `MODIFY` and `CHANGE` restate a column in full. Cost: two more columns in one existing query.
- **D3, shared fragments take SQL text.** `ddl::column_sql` and `ddl::foreign_key_sql` are shared by the designer and the export `Writer`, whose output is byte-identical. Cost: see Known limits (MySQL comment backslash).
- **D4, where MySQL splits.** Described above. Cost: at most 2 statements, so the worst MySQL failure is "1 of 2 statements were applied".
- **D5, row count for Drop table.** A bounded `SELECT COUNT(*)` over at most 10,001 rows fills the warning ("1,204 rows" or "more than 10,000 rows"), because the tree's figure is a catalog estimate that can read 0 on a fresh table. It runs on a short-lived query session and is best effort: when it fails the warning says the count is unknown. Cost: one bounded scan per Drop preview.
- **D6, incoming Foreign Keys.** `TableDesign.referenced_by` lists the keys that point at the table, so the Drop warning can name them.
- **D7, New table and Drop table live in row menus.** Database rows (MySQL, SQLite), schema rows (PostgreSQL) and Tables folders get "New table..."; table rows get "Open", "Design table" and "Drop table...". Read-only Connections get neither New table nor Drop table; Design table stays and opens View only. Drop always asks: `ConfirmDrop` on a plain Connection, `ConfirmRun` with verb "Drop" on Production. Cost: one dialog on plain Connections the spec did not draw.
- **D8, SQLite rebuild details.** Described above. SQLite Foreign Keys have no names, so the read model names them `fk_<id>`; a rowid-alias primary key is the index `primary` with no saved SQL. Cost: tables with a `CHECK`, a collation inside a constraint or an expression, or the other saved-text clauses above are copy-only; column collations are carried (S4).
- **D9, PostgreSQL increment.** Only identity columns toggle. A serial column shows Auto-increment on and disabled, "Serial column: change its default instead."
- **D10, PostgreSQL type change** is `ALTER COLUMN c TYPE t`, with `USING` only where needed. S5 and S7 change how narrowing is written (below).
- **D11, Drop with Pending Edits asks before.** Drop first runs the leave ask over that table's grid tab and design tab; Cancel stops the drop. After the drop the tabs close without a second ask.
- **D12, MySQL partial failure is history.** Cost: see Known limits (history shows the first statement).
- **D13, one leave dialog, two verbs.** The grid tab and the design tab each register their own control; the App's leave ask picks "Save" or "Apply" by the tab's kind ("Apply changes to orders?"). Both tabs of one table can be dirty; each is asked about in turn.
- **D14, DDL for Read-only.** Read-only shows the table's DDL in place of the preview, through `table_ddl`. S11 changes how PostgreSQL writes it.
- **D15, the designer is its own tab** (user decision). Tab kind `design`, title "orders design", `edit` icon, dirty star, lock on Read-only, PROD chip and Group underline like any place tab, opened from the table row menu or the grid's Design button (tables only). It stays mounted while hidden, like table tabs. Cost: none against the frames; the spec's Data | Design switch is gone. (Items 42 and 48: the tab now shows the designer feature icon, and tabs have no Group underline.)
- **D16, Columns order differs from the frame.** Name, Type, Nullable, Default, Auto-increment, Key, Comment. The frame has no Auto-increment column; it is kept because the Core needs the toggle (D9). Comment is absent on SQLite. Key draws `key` for the primary key and `link` for a column in a Foreign Key. Cost: one more column than the frame (S1).
- **D17, Indexes tab shows Method and Where.** Partial and expression indexes are rows that allow rename and drop only. Creating an index with a method or a Where stays out of scope (S1).
- **D18, Foreign keys References column.** One column holding the target table and its columns, read as "customers (id)".
- **D19, toolbar.** Tab counts, then Add (label follows the tab), Remove, Move up, Move down. On PostgreSQL alter targets Move is disabled with "PostgreSQL cannot reorder columns".
- **D20, Read-only.** Same tabs, every control disabled, "View only" chip with a lock, the Read-only sentence, and a taller bottom pane titled "DDL".
- **D21, header strip.** One 36 px strip built from the grid's `table-header` classes, with the Production wash like the grid.
- **D22, SQL preview island.** "SQL preview", the per-mode line, a Copy button, warnings above the SQL. The SQL uses the Settings > Editor font.
- **D23, tab titles.** "orders design", and "New table" until the table is created.
- **D24, designed from the nearest patterns.** New table and Drop table have no frame; they use the tree's row menus, `Dialog`, `SqlBlock` and the warning banner.
- **D25, Production Apply.** "Apply on PROD" opens `ConfirmRun` titled "Apply on freight-prod · shop", button "Apply on freight-prod".
- **D26, type suggestions use a native `datalist`.** The Type cell must take any SQL type and the shared `Select` takes only listed values. Cost: see Known limits.
- **D27, designer keys are local, like the grid's.** Ctrl+S applies, Ctrl+N adds a row on the active tab, Delete removes, Alt+ArrowUp and Alt+ArrowDown move; the designer handles them and stops them reaching the window command bus. Cost: see Known limits.
- **D28, Recent forgets a dropped table.** `forget_recent` removes that table's Recent items; no store schema change (`SCHEMA_VERSION` stays 3).
- **D29, status bar through the slot.** A visible design tab shows "{n} columns" and ", {m} changes" in the window status bar.

## Rulings taken while building (S1 to S14)

These override or extend a D ruling. Each closes a path that a review reproduced.

- **S1, frame differences kept.** D16 (Auto-increment column) and D17 (Method and Where read-only) as the re-check recommended. Cost if wrong: a small UI change later.
- **S2, the AUTOINCREMENT keyword and "advanced" indexes and keys.** The SQLite read model records the `AUTOINCREMENT` keyword apart from the rowid alias, and the writer emits it only when it was there. Indexes and Foreign Keys with an attribute the model does not carry (PostgreSQL `INCLUDE`, sort order, operator class, collation, `NULLS NOT DISTINCT`; MySQL prefix length, `DESC`, `FULLTEXT`; Foreign Key `DEFERRABLE` or `MATCH`) read as `advanced`, with a note. The designer offers rename and drop only, and any plan that would recreate one is refused with a warning naming it. Cost: such tables need SQL for those edits.
- **S3, PostgreSQL literals safe under either `standard_conforming_strings`.** Text holding a backslash is written as `E'...'` with backslashes and quotes doubled, for designer comments and defaults, export comments and the 5b row edits. The session setting is not changed, so typed queries still read backslashes as the person expects. Cost: none.
- **S4, column collation.** `TableColumn.collation` is read on all three Dialects (only when not the default) and kept in ALTER, CREATE and the rebuild; an index is advanced only for an index-level collation that differs from its column's. Cost: none.
- **S5, PostgreSQL narrowing refuses instead of truncating** (overrides D10). A length or precision cut within a type family has no explicit cast, so the server refuses values that do not fit and the transaction rolls back. The narrowing warning stays. Cost: a narrowing with bad rows fails and the person must fix the data first.
- **S6, defaults across a type change, MySQL timestamp range, MySQL advanced columns.** (a) A PostgreSQL type change on a column with a default runs `DROP DEFAULT`, `TYPE`, `SET DEFAULT`. (b) MySQL `date` or `datetime` to `timestamp` is a narrowing with a warning about the 1970 to 2038 range. (c) MySQL columns with `INVISIBLE`, `SRID`, `COLUMN_FORMAT`, `STORAGE` or `ENGINE_ATTRIBUTE` read as advanced: they can be renamed (`RENAME COLUMN`, no restatement) or dropped, and any edit that would restate them is refused with a warning naming the attribute. Cost: such columns need SQL for those edits.
- **S7, cross-family changes into length-limited types refuse too** (extends S5). A change into a limited string or bit type casts to the unlimited base type (`::text`, `::bpchar`, `::varbit`) so the server applies the limit and refuses values that do not fit; integer to `bit(n)` is refused with "change it in SQL". The warning says values are rounded for numeric scale and time precision cuts, which the server cannot refuse. MySQL `SHOW CREATE TABLE` names are read in both backquote and `ANSI_QUOTES` forms, and a column line that cannot be parsed reads advanced. Cost: none.
- **S8, SQLite rebuild rules.** Every non-literal SQLite default is written in parentheses (an expression default otherwise breaks the new `CREATE TABLE`); identifier-style defaults (`"abc"`, `[abc]`, `active`) are written as string literals. `INSTEAD OF` triggers of dropped views are recreated. `foreign_key_check` runs for the table and every referencing table, schema-qualified. The rebuild always turns `foreign_keys` off before the transaction and always runs the checks, whatever the pragma read at load. An advanced SQLite index with saved SQL is recreated verbatim from that SQL; an advanced Foreign Key still refuses a rebuild. Cost: pre-existing key violations now block a rebuild; accepted as safer.
- **S9, `foreign_keys` is read again at Apply.** The plan records the value read at load; the runner reads `PRAGMA foreign_keys` again before the first statement and refuses with "reload the table" on a mismatch, so the value restored afterwards is always the one in force at Apply. Cost: one extra reload in a rare case.
- **S10, the D4 split is kept** for dropping a Foreign Key with its index, although MySQL 8.0.30 accepts the merged form. Older MySQL and MariaDB servers refuse it. Cost: a two-statement plan where one would do.
- **S11, PostgreSQL DDL from the server** (overrides D14 on PostgreSQL). `table_ddl` writes indexes with `pg_get_indexdef` and constraints, including `CHECK` and `EXCLUDE`, with `pg_get_constraintdef`; generated columns and identity `ALWAYS` or `BY DEFAULT` are written as the server has them. A failed restore statement after Apply returns a structured error that says whether the change was applied, and an applied change still gets its history entry. Cost: about 150 lines; the DDL shown must match the server or it misleads.
- **S12, removing a column drops loaded indexes and keys whole.** Removing a loaded column drops every loaded index, primary key and Foreign Key that contains it, never narrowed, with a designer note naming each plain index (unique indexes, primary keys and Foreign Keys already get Core warnings). Only indexes and keys added in the draft are shortened. Restore puts a dropped loaded index or key back only when none of its columns is still removed, matched by id and column set, so any remove and restore order is correct. This matches PostgreSQL's `DROP COLUMN` and never silently changes uniqueness. Cost: the person re-adds a narrower index by hand.
- **S13, the UI side of Apply.** After any Apply that changed the database the draft is spent until the reload lands; Apply runs only when the freshly planned statements equal the ones the preview shows ("The preview changed. Check it and Apply again."); a new table's automatic key and index names follow its final name. Cost: one extra Apply press after a fast edit.
- **S14, Apply re-checks the table; SQLite drops name their child actions; one expression means no top-level comma.** (a) Every Alter and Drop checks the table against the loaded design before the first write. SQLite compares, inside the runner's `BEGIN IMMEDIATE` transaction, the saved SQL in `sqlite_schema` of the table, its indexes and triggers, and the loaded views and their triggers with what was loaded. MySQL and PostgreSQL read `table_design` again at Apply and compare it with the request's design. Any difference refuses with "The table changed since it was opened. Reload it and make the change again."; nothing is planned again, so the pass hashes are unchanged. (b) With Foreign Keys on, SQLite's `DROP TABLE` first deletes every row, which runs each child key's ON DELETE action. The Drop plan names each child table and its action ("Dropping customers also deletes the matching rows in orders.", "... also clears the key in notes on the matching rows."; NO ACTION and RESTRICT: "fails while rows in audit point at it"), and records the loaded `foreign_keys` value so S9 refuses a drop whose enforcement changed. The design also carries the saved `CREATE TABLE` of each child table, and a SQLite Drop refuses when the set of child tables or any of their saved SQL changed since loading (S15). SET NULL and SET DEFAULT fail instead when the child key is required or its default is not NULL; the warning says so. (c) `check_fragment` refuses a `,` outside parentheses, brackets and quotes (so PostgreSQL `ARRAY[1, 2]` still passes, S15), so a type or default such as `0, DROP COLUMN email` cannot add a clause. (d) A design pass covers every statement of the plan, its checks included. Cost: an extra reload when someone else changed the table.

### Accepted deviation

- **MySQL clause order is the edited order.** The plan listed a fixed clause order for the merged `ALTER TABLE`. The planner writes the column clauses in the order of the edits instead, because `ADD COLUMN ... AFTER x` and `MODIFY ... AFTER x` need the column they name to exist at that point. Drops still come first and key adds last.

## Known limits

- **MySQL comment backslash (D3).** Comment literals double backslashes, so under `NO_BACKSLASH_ESCAPES` a MySQL comment holding `\` is stored with the backslash doubled. The same holds for a loaded string default that a `MODIFY` or `CHANGE` restates, and a restated BIT or BINARY column's default may not round-trip.
- **PostgreSQL serial (D9).** Auto-increment on a serial column cannot be toggled; change its default in SQL. Adding identity to a table with rows starts at 1.
- **SQLite saved-text clauses are copy-only (D8).** A table with a `COLLATE` inside a constraint or an expression (column collations are carried, S4), `CHECK`, generated columns, `ON CONFLICT`, `WITHOUT ROWID` or `STRICT` in its saved text can be renamed and indexed in place but not rebuilt by the designer.
- **History shows the first statement (D12).** A multi-statement entry is one row whose first line shows, with an ellipsis.
- **Native type suggestions (D26).** The Type cell's suggestion list is native WebView chrome, unlike the rest of the app; it waits for a free-text combobox.
- **No registry commands (D27).** The command registry has no focus context, so the designer's keys are local and not rebindable. `design.apply` and its friends join the registry once it has one.
- **PostgreSQL DDL coverage (S11).** The Read-only DDL leaves out sequence options, storage and compression settings, and partitioning.
- **SQLite double-quoted unknown names.** In a SQLite index, a double-quoted name that is not a column is read by SQLite as a string literal. The planner refuses such an index, so it never reaches the server.
- **SQLite browse connection.** The browse connection runs with `foreign_keys` on; the rebuild turns it off and restores it around its transaction (S8, S9). A Drop runs with it on, so child keys' ON DELETE actions run, and the warning names them (S14).
- **The MySQL and PostgreSQL re-check is not atomic (S14).** The table is read again just before the change runs, not under a lock, so a change made in that instant is not seen.
- **Removed columns in partial or expression indexes (S12).** Whether such an index uses a removed column is found by a whole-word match on its SQL text, so it can drop one that only mentions the name. The index is named in the note and can be restored.
- **Advanced indexes, keys and columns (S2, S6).** They can be renamed and dropped only.
- **PostgreSQL cannot reorder columns.** Move is off on PostgreSQL alter targets.
